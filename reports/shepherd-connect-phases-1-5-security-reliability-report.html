Phase-by-phase implementation

Phase 1 — Authentication boundary and user-record privacy

COMPLETE

Implemented

  • JWT signature and expiry remain intact, followed by a current PostgreSQL user lookup.
  • Deleted, inactive, suspended, rejected, or otherwise disallowed accounts are rejected immediately.
  • The selected role in the token must still belong to the current primary or secondary role set.
  • The request principal is rebuilt from authoritative database state.
  • GET /api/users/:id permits self, admin, and super admin access; unauthorized cross-user access is concealed as the same 404 shape used for absent records.
  • The predictable session-secret fallback was removed; missing configuration fails closed without generating, printing, or mutating a secret.

Preserved

  • Existing JWT format and 24-hour expiry.
  • Current-device logout and role switching.
  • Existing frontend token handling and sanitized user responses.
  • No schema, frontend, dependency, API, or deployment redesign.

Accepted limitation: Phase 1 intentionally did not make password change/reset revoke an otherwise valid token. A separate account-security/session-invalidation task remains appropriate.

Phase 2 — Registration OTP security and abuse prevention

COMPLETE
  • Six-digit registration OTPs use cryptographic randomness.
  • Stored OTP values are versioned, domain-separated HMAC digests; plaintext legacy rows fail closed.
  • Email and phone proofs are canonicalized and bound to the exact typed contact being registered.
  • Issuance limits are enforced per IP, per contact, with a resend cooldown and one active OTP per contact.
  • Five durable failed attempts exhaust an OTP session.
  • Verification is an atomic PostgreSQL transition using database time; one concurrent correct verification can win.
  • Registration requires a verified server-side otpPinId, consumed in the same transaction as the user/role mutation.
  • Rollback preserves a proof when the registration mutation fails; concurrent proof reuse yields at most one registration mutation.
  • Provider failures return bounded generic responses without leaking OTPs or provider internals.
Control Enforced policy
Validity 10 minutes, evaluated with PostgreSQL time
Per-IP issuance 10 requests per 15 minutes
Per-contact issuance 5 attempts per rolling hour
Resend cooldown 60 seconds
Verification attempts Maximum 5 failed attempts

Password-reset, MFA, and delegate/pickup OTP behavior were intentionally preserved outside this phase.

Phase 3 — Multi-role concurrency and role integrity

COMPLETE
  • All existing-user role decisions lock the target user row with SELECT ... FOR UPDATE before reading role state.
  • Primary, secondary, and pending role sets are calculated from locked authoritative state.
  • Role values are canonicalized with set semantics: no duplicate secondary/pending roles and no primary/secondary duplication.
  • Approving or rejecting one pending role preserves unrelated pending and approved roles.
  • Grant, revoke, primary-role change, reassignment, teacher promotion, and registration role paths serialize on the same user row.
  • Two distinct valid OTP proofs requesting different roles can both succeed without losing either durable outcome.
  • A removed-role token is rejected while tokens for remaining roles continue to work.
Architecture retained. No normalized role table, role-version column, schema migration, API-contract change, frontend change, or authorization redesign was introduced.

Phase 4 — Attendance and offline integrity

COMPLETE

Attendance transitions

  • Check-in, escort, arrival, checkout, staff checkpoint, clock-out, and emergency-out are idempotent under retries and concurrency.
  • Only the winning conditional transition writes timestamps/actors and produces side effects.
  • Exact retries return the authoritative existing result without rewriting provenance.
  • Intentional same-day multi-service behavior is preserved while opposing active slots remain blocked.
  • Attendance-specific event identity distinguishes a retry from a legitimate new check-in after pickup.

Offline safety

  • Queues are partitioned by authenticated user ID and cleared according to logout policy.
  • Account switching never reassigns one user’s queued events to another.
  • Every sync revalidates current account, role, and object authorization.
  • Events older than 24 hours or outside the authoritative WAT service date are rejected.
  • Event type is dispatched explicitly; checkout data cannot replay as check-in.
  • Queued check-ins retain attendant provenance.

Implicit service dates, Sundays, and weekday calculations use Africa/Lagos authority across the relevant frontend and backend attendance flows. PostgreSQL concurrency tests run automatically through the development database gate.

Phase 5 — Notification outbox, SSE, and operational reliability

COMPLETE

Transactional notification outbox

  • PostgreSQL is the sole delivery coordination mechanism; no broker or new dependency was added.
  • The existing notifications table remains the authoritative user-visible in-app projection.
  • For required consequences, domain mutation, in-app projection, and external delivery intent commit in one PostgreSQL transaction.
  • Provider calls always happen outside the domain transaction; provider failure cannot roll back committed domain state.
  • One outbox row represents one logical notification, recipient, channel, and template generation.
  • A PostgreSQL unique logical key enforces deduplication, including late-pickup reruns.
  • Attendance parent intents use WhatsApp, SMS, and email; teacher intents use WhatsApp only.
  • WhatsApp remains preference-gated. Required SMS/email behavior is preserved when communication preferences are absent.

Worker correctness

  • Eligible rows are claimed with FOR UPDATE SKIP LOCKED, an unpredictable claim token, and a bounded lease.
  • A stale worker cannot finalize a row after lease expiry and reclaim.
  • Clearly retryable failures use a bounded five-attempt schedule of approximately 30 seconds, 2 minutes, 10 minutes, 30 minutes, and 2 hours.
  • Ambiguous post-submission outcomes become terminal uncertain; they are not blindly retried or switched to another provider.
  • accepted means provider submission acceptance, never handset/inbox delivery.
  • Failures are classified, redacted, and bounded; operational history exposes attempts, next retry, provider acceptance, uncertainty, and safe-to-retry state.
  • Legacy WhatsApp pending rows migrate idempotently before worker startup: unclaimed work becomes pending; previously claimed unfinished work becomes uncertain.
State Meaning
pending / processing / retryable Active coordination states; only retryable failures are scheduled again.
accepted Provider accepted/submitted the request; final delivery is not asserted.
uncertain Provider may have accepted before connection loss; automatic delivery stops.
skipped Delivery is intentionally not attempted, such as missing contact or disabled preference.
dead_letter Retry budget exhausted or permanent processing failure.

SSE credential hardening

  • The normal bearer JWT is removed from the EventSource URL.
  • An authenticated POST mints a short-lived, purpose-bound one-time ticket; only its SHA-256 hash is stored.
  • The ticket is bound to user, selected role, purpose, expiry, and consumed state.
  • The ticket is transmitted in an HttpOnly, SameSite Strict cookie scoped to /api/events; Secure is enabled for production HTTPS.
  • GET redemption atomically consumes the ticket and revalidates current user/account/role state.
  • Streams are bounded to five minutes. Every reconnect closes the prior EventSource, mints a fresh ticket, opens a token-free URL, and refetches authoritative state.
  • SSE remains an invalidation hint; no replay or Last-Event-ID durability was introduced.

Lifecycle and operational controls

  • Empty broadcast and pre-dismissal audiences do not consume the 60-second send lock.
  • Unsupported SMS/email broadcast requests fail explicitly rather than being silently skipped.
  • Terminal outbox coordination records are retained for 90 days.
  • Expired or consumed SSE tickets are retained for one day.
  • Phase 5 user references are removed before notification/user deletion, preventing the new outbox and ticket FKs from introducing a deletion regression.

Known limitations and operator guidance

  • External exactly-once delivery is not claimed. PostgreSQL deduplicates application intents and worker attempts, but providers may accept a request before a connection loss becomes visible. Such rows are intentionally marked uncertain for human review.
  • Accepted is not delivered. Final provider delivery/read receipts are not processed in Phase 5.
  • Manual resend must be explicit. A new resend generation is required; the original logical deduplication key must not be bypassed silently.
  • SSE is not durable storage. A missed stream event is recovered by refetching authoritative in-app state, not by stream replay.
  • Existing broad user-deletion limitations remain. Historical rows in unrelated attendance, classroom, safeguarding, scheduling, and other tables can still block deletion depending on their current retention policy. Phase 5 prevents its two new FK categories from making this worse; changing broader deletion/retention semantics requires separate approval.
  • Production rollout remains outstanding. Production requires an approved schema rollout, release process, and post-release observation. This report does not assert that Phase 5 is live in production.
Do not publish from this report alone. Before production rollout, obtain human approval for the database schema migration, release checkpoint, provider configuration review, and operational monitoring plan.
