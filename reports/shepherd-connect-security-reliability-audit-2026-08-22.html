This audit combined direct source inspection, three independent focused architecture reviews, dependency analysis, static application security testing, privacy/dataflow scanning, TypeScript checks, and the existing automated test suite.

  • Important limitation: this was not an authenticated penetration test against production. Database privileges, bucket policy, production-only environment settings, third-party retention terms, and runtime logs remain partly unverified.
  • Endpoint inventory: 242 route declarations were found. High-risk routes were inspected directly; this first pass does not claim exhaustive manual proof for every endpoint.

C. Critical findings

CRITICALP0Unauthenticated users can register as super admin

Evidence: lib/api-zod/src/generated/api.ts RegisterBody accepts super_admin; artifacts/api-server/src/routes/auth.ts includes it in accepted roles, while approval is required only for admin and teacher. New non-approval users are activated and immediately receive a JWT.

Impact: complete administrative takeover, access to child/family data, user and role administration, safeguarding data, settings, exports, and operational controls.

Reproduction: submit a valid registration body with role super_admin, then use the returned token.

Smallest safe fix: remove privileged roles from public registration. Permit only parent registration publicly; bootstrap the first super admin out-of-band and require existing super-admin approval for every staff role.

Test: public registration with super_admin/admin/teacher/support/attendant must be rejected; only approved server-side role changes may grant staff access.

D. High findings

HIGHP0Pickup streams and class queues expose children without authentication

Evidence: pickupRequests.ts GET /pickup-requests/stream/:classNumber and GET /pickup-requests/:classId have no authentication. Queue records include child name, parent name, class, and pickup time.

Impact: anyone who can reach the API can enumerate live child pickup activity. Classroom-display routes are also public.

Fix/test: require a narrowly scoped classroom-display credential or authenticated allocated staff role; return minimal fields; prove anonymous and cross-class requests are denied.

HIGHP0Any authenticated account can create or dismiss another child’s pickup request

Evidence: POST /pickup-requests has authentication but no parent ownership check or parent-only role guard; DELETE /pickup-requests/:id accepts any authenticated user.

Impact: a parent, teacher, or compromised low-privilege account can create false pickup alerts for any checked-in child or remove legitimate alerts.

Fix/test: require parent ownership for creation and allocated teacher/support/admin authority for dismissal; add User A versus User B tests.

HIGHP0“Private” uploaded objects are publicly downloadable

Evidence: GET /storage/objects/* in routes/storage.ts has no auth or ACL check; the provided protected-route block is commented out.

Impact: possession or discovery of an object path can expose child photos and other private uploads.

Fix/test: authenticate, map each object to an owner/resource, enforce READ permission, use non-guessable paths only as defense-in-depth, and test parent/teacher/cross-family access.

HIGHP0QR and face scan endpoints disclose sensitive child data to any authenticated user

Evidence: attendance.ts scan-qr and scan-face use only authMiddleware. QR responses include family data, children, attendance history, class, allergies, and medical-alert indicators; QR scan may also persist automatic class assignment. Face scan compares against all enrolled biometric descriptors.

Impact: low-privilege users can obtain another family’s sensitive child records with a code/descriptor and may trigger data mutation.

Fix/test: restrict to check-in desk roles, minimize response fields, separate lookup from mutation, rate-limit biometric matching, and test every role.

HIGHP1Authenticated API responses persist in browser Cache Storage across logout

Evidence: src/sw.ts caches successful /api/* responses for 24 hours. contexts/auth.tsx clears React Query and localStorage on logout but does not clear Workbox Cache Storage.

Impact: a later account or offline user on the same device can receive prior-user family, child, attendance, or safeguarding responses.

Fix/test: never cache authenticated API responses; purge prior API caches on activation/logout; test two users sequentially on one browser, including offline mode.

HIGHP1WhatsApp webhook authentication fails open

Evidence: webhooks.ts returns true from signature validation when TWILIO_AUTH_TOKEN is absent. The webhook trusts the sender phone number to look up a parent and returns child/check-in information. It also logs phone and message content.

Impact: a missing production secret turns the endpoint into a spoofable child-information oracle. Logs retain unnecessary personal data.

Fix/test: fail closed in production when the secret is absent; verify exact public URL/raw parameters; reject invalid signatures; redact message/phone logs.

HIGHP1Report export builds executable HTML from unescaped data

Evidence: pages/reports/index.tsx interpolates titles, columns, rows, metadata, and existing innerHTML into document.write.

Impact: stored names, feedback, or report values containing HTML can execute script in the report popup and access the app origin.

Fix/test: construct text nodes/DOM or centrally HTML-escape every untrusted value; add payload tests for script, event-handler, SVG, and closing-tag vectors.

E. Medium findings

  • JWT/session lifecycle: logout is client-side only; password change/reset does not invalidate existing 24-hour JWTs. Add token version or server-side session revocation.
  • Unsafe JWT fallback: middlewares/auth.ts contains a public fallback secret. Normal app startup currently fails closed in routes/auth.ts if SESSION_SECRET is absent, but the fallback remains dangerous in tests, partial imports, or future refactors.
  • Registration verification gap: the registration API does not bind a successful OTP session to the subsequent registration request. Backend clients can bypass the UI’s verification sequence.
  • Abuse controls: global 300/minute limiting exists, and reset verification has a tighter limiter, but login, forgot-password, send-otp, verify-otp, scan, upload-ticket, and AI-facing routes lack route/account/contact-specific protections.
  • Attendance races: “arrive” reads state and then updates by ID without a status guard; concurrent checkout can be overwritten. QR auto-processing performs multi-record insert/update/intent completion without a transaction, allowing partial family processing.
  • Upload validation: upload-ticket issuance accepts client-declared name, size, and content type without demonstrated server-enforced content limits or post-upload MIME verification.
  • In-memory pickup queue: pickup state is process-local, lost on restart, and inconsistent across autoscale instances.
  • Scheduler locks fail open: database lock errors cause each instance to run the job, creating duplicate notifications or cleanup under outage conditions.
  • External notification reliability: many attendance notifications are fire-and-forget; delivery failure is logged or discarded without a durable outbox/retry/status.
  • WhatsApp queue claiming: the worker does not verify that its conditional update actually claimed an item before sending. Concurrent workers can send duplicates; crash recovery intentionally marks uncertain sends failed.
  • Guest cleanup: child/family deletion is not transactional and can fail on attendance foreign keys, leaving partial cleanup.
  • AI/privacy: WhatsApp text and children’s names, plus feedback comments, can be sent to the configured AI provider without visible minimization, consent/notice, retention control, or privacy tests.
  • CORS and headers: unrestricted cors() is enabled. A documented production origin allowlist, Helmet-equivalent headers, and CSP were not evidenced.
  • Frontend route guards: the UI applies authentication but not per-route role restrictions. Backend controls remain mandatory; direct navigation may expose inappropriate screens or trigger excess data requests.

F. Low findings

  • SAST reported one medium “tainted redirect” at the fixed custom-domain redirect. The destination host is constant and only the original path/query is appended, so open-domain redirect exploitability is not proven; validate/encode the path and retain an allowlisted destination.
  • Error boundaries show raw error.message to users. Replace with a correlation ID and generic message in production.
  • Some dialogs use fixed 460–480px widths and may overflow narrow devices; mobile/accessibility behavior has no automated proof.
  • Several date calculations use UTC/local time while business rules use WAT. The recent drop-off intent lookup is WAT-safe, but the whole application is not consistently normalized.

G. Unknown / unverified areas

  • Production database least-privilege role, encryption, backup restore testing, row-level security, and network exposure.
  • Object bucket-level public access configuration and whether historical object URLs have leaked.
  • Production environment parity, secret rotation dates, webhook secret presence, and deployment rollback procedure.
  • Git-history secret exposure; HoundDog reported zero findings in the current scan, but historical repository scanning was not independently proven.
  • External provider retention, data residency, contractual safeguards, and consent for minors’ information sent by SMS, email, WhatsApp, push, or AI.
  • Runtime authorization behavior for all 242 declared routes; this audit directly verified high-risk examples, not every identifier on every method.
  • Browser/device compatibility, WCAG conformance, malware scanning, disaster recovery, and incident response.
  • MFA recovery and lockout behavior, refresh token behavior (none identified), and forced logout after account suspension.

J. Authentication review

Overall: FAIL

  • Positive controls: bcrypt password hashing, generic invalid-credential responses, 24-hour JWT expiry, optional TOTP MFA, one-time OTP deletion, password-reset expiry and limited verification attempts.
  • Critical failure: public privileged-role registration.
  • Session weaknesses: no server-side logout, token revocation, password-change invalidation, or account-state recheck on each JWT request.
  • Registration weakness: OTP verification is not cryptographically/server-side bound to registration.
  • Reset weakness: six-digit reset tokens are stored plaintext; verification is IP-limited but not clearly account/contact limited.
  • MFA unknown: enrollment, confirmation, recovery, and replay protections were not fully exercised.

K. Authorization / IDOR / BOLA review

Overall: FAIL

Many administrative endpoints correctly use requireRoles, and existing smoke tests prove selected anonymous and insufficient-role denials. However, authorization is not default-deny and several sensitive resources rely on authentication alone.

  • Pickup requests: public read; unscoped create/dismiss.
  • Attendance scan: unscoped family, child, health, attendance, and biometric access.
  • Object storage: no private-object authorization.
  • Frontend: authenticated route wrapper only; per-page role restriction is absent.
  • Required pattern: role + resource ownership/allocation + minimal projection on every read and mutation; automated User A/User B matrices for all ID-bearing resources.

L. API security review

Overall: FAIL

  • Input validation is inconsistent: important routes use Zod, while others destructure/cast raw bodies and accept unbounded arrays/strings.
  • Global rate limiting is present, but sensitive per-route and per-identity controls are incomplete.
  • Public SSE/queue and storage routes expose sensitive data.
  • Idempotency exists for attendance uniqueness but not as a general mutation contract.
  • Audit logging is available but not systematically applied to all high-risk operations.
  • CORS is unrestricted; security headers/CSP are not evidenced.
  • No confirmed raw SQL injection or command injection was found in reviewed code.

M. Database review

Result: PARTIAL / FAIL for workflow safety.

  • Pass: typed ORM, parameterized raw scheduler query, foreign keys, and an attendance unique index provide useful integrity controls.
  • Fail: multi-step QR processing, cleanup, and some transitions are not transactional.
  • Fail: read-then-write status changes lack compare-and-set guards.
  • Fail: async delivery is not transactionally coupled to business events.
  • Unknown: production DB role permissions, backup/restore, encryption, RLS, statement timeouts, and migration rollback.

P. Secrets review

Current-tree result: no credential value was reported by HoundDog, and no secret value was printed during this audit.

  • Fail: source contains a hardcoded JWT fallback string, even though normal app startup also checks for the required environment secret.
  • Pass: service credentials are referenced through environment variables rather than embedded values in reviewed source.
  • Unknown: Git history, prior logs/build artifacts, rotation cadence, production-vs-development secret separation, and provider-side permission scope.

Q. AI / LLM security review

Result: PARTIAL / FAIL for privacy governance.

  • AI calls are server-side; API credentials are not intentionally shipped to the browser.
  • The model performs intent/sentiment classification, not authorization. No direct AI-generated SQL or code execution was found.
  • Children’s names and user messages can be included in model prompts; feedback comments are also analyzed externally.
  • Model JSON is parsed with weak semantic validation; fallback is safe-ish but output ranges/allowed intents should be schema validated.
  • Missing evidence: consent/notice, minimization/redaction, retention terms, spend/rate controls, prompt-injection tests, and cross-user context tests.

R. Failure and reliability review

Overall: FAIL

  • Database unavailable: global error middleware prevents silent crashes in many cases, but targeted retry is used narrowly and scheduler locking fails open.
  • External provider unavailable: user-facing business actions often succeed while notifications fail asynchronously without durable status/retry.
  • Duplicate request: attendance unique constraints help check-in, but pickup and other operations lack broad idempotency.
  • Process restart: pickup queue is lost; WhatsApp recovery exists but has uncertain-send and concurrency limitations.
  • Concurrent actions: arrival/checkout and multi-child QR flow have race/partial-write windows.
  • Session expiry: client inactivity logout exists, but server JWT remains valid and cached API responses remain on-device.
  • Observability: structured logging and error-log persistence exist; sensitive webhook content is over-logged, while delivery success/failure lacks a unified audit trail.

U. Mandatory AI safe-change protocol

  1. Read the relevant code, schemas, route registration, and existing tests before editing.
  2. List affected files, user journeys, authorization boundaries, data classifications, and database changes.
  3. State the smallest proposed change and likely regressions.
  4. For high-risk files/behavior, obtain explicit human approval before editing.
  5. Make the smallest scoped change; do not refactor unrelated code or replace working architecture.
  6. Never trust frontend role/ownership checks; prove the server rule.
  7. Add a failing regression test first for security bugs where practical.
  8. Use transactions/conditional writes for multi-step or concurrent state changes.
  9. Do not silently change schemas, auth, roles, environment variables, providers, deployment, or production data.
  10. Run tests, typecheck, build, and relevant security checks before and after high-impact changes.
  11. Show changed files and a concise diff summary; report failures honestly.
  12. Never suppress tests, scanner findings, or dependency checks merely to obtain green output.
  13. Do not delete tests without explicit approval.
  14. For releases, prove cross-role and cross-tenant denial, not only the happy path.
  15. Record deployment/schema consequences before asking the human to publish.

X. Fix order

P0 — must fix before any release

  1. Close public super-admin/staff registration and invalidate unauthorized accounts/tokens after a controlled review.
  2. Protect pickup streams/queues and enforce parent ownership plus staff dismissal scope.
  3. Protect private objects with server-side ACLs.
  4. Restrict QR/face scanning to intended desk roles and minimize returned child data.

P1 — must fix before production

  1. Stop caching authenticated APIs and purge existing API caches.
  2. Fail closed on webhook verification and redact sensitive logs.
  3. Remove report XSS and introduce CSP/security headers.
  4. Add server-side session invalidation and bind OTP verification to registration.
  5. Make attendance transitions and QR processing atomic/idempotent.
  6. Persist pickup state and make scheduler/WhatsApp claiming safe across instances.
  7. Triage and patch exposed high dependency advisories without forced upgrades.

P2 — should fix

Durable notification outbox, upload MIME/size enforcement, AI privacy controls, unified WAT date handling, per-route abuse controls, comprehensive route-level IDOR suite.

P3 — improvement

Frontend role-aware navigation, accessibility/responsive automation, generic production errors, expanded operational dashboards and runbooks.

Y. Release verdict

NOT SAFE FOR PRODUCTION

The app compiles and its existing tests pass, but those tests do not cover the release-blocking boundaries. Public super-admin registration alone permits full takeover. Public pickup data, unprotected private objects, and overly broad scan access expose children’s information. These are source-confirmed failures, not theoretical scanner-only concerns.

Development may continue in a controlled environment. Do not publish a new release until P0 issues are fixed, unauthorized production accounts/tokens are reviewed, and the required denial tests pass. P1 items should then be completed before declaring the system production-ready.
