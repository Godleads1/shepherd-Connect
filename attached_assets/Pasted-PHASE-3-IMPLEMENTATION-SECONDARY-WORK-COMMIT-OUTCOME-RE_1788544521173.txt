PHASE 3 IMPLEMENTATION — SECONDARY WORK / COMMIT-OUTCOME RELIABILITY

The Phase 3 diagnostic investigation is approved.

You are now authorized to IMPLEMENT Phase 3, but only within the narrowly defined scope below.

Do not interpret this as permission for a general reliability refactor.

==================================================
PRIMARY OBJECTIVE
==================================================

Ensure that failure of NON-AUTHORITATIVE secondary work cannot make an already-committed authoritative mutation appear to have failed.

The governing rule is:

AUTHORITATIVE BUSINESS OUTCOME
must be determined by the authoritative transaction/state transition.

SECONDARY WORK
must not redefine that outcome after commit.

Do not apply checkout-style operation identity to every route.

Do not create a universal idempotency framework.

Do not redesign the application globally.

==================================================
MANDATORY PRE-IMPLEMENTATION STEP
==================================================

Before changing each route, create a route-level classification:

1. AUTHORITATIVE
2. REQUIRED PRE-COMMIT VALIDATION
3. REQUIRED TRANSACTIONAL OUTBOX/INTENT
4. OPTIONAL SECONDARY EFFECT
5. RESPONSE ENRICHMENT
6. PARTIAL-MULTI-WRITE COMMAND

For every route you modify, document internally which category each operation belongs to.

If classification is uncertain, STOP implementation for that route and report it.

Do not guess.

==================================================

Implement the 8 confirmed routes:

- POST /teacher-allocations/assign-duty
- POST /teacher-allocations/auto-schedule
- POST /teacher-allocations/:id/swap
- POST /teacher-allocations/:id/mark-unavailable
- POST /pickup-delegates
- POST /family-assist/delegate

For EACH route independently classify the notification as:

A. REQUIRED TO THE BUSINESS COMMAND

OR

B. OPTIONAL SECONDARY EFFECT

Do not assume.

### If REQUIRED:

The notification intent/outbox write must participate in the authoritative transaction.

Desired sequence:

AUTHORITATIVE DOMAIN MUTATION
+
REQUIRED NOTIFICATION INTENT
↓
SINGLE TRANSACTION
↓
COMMIT
↓
HTTP SUCCESS
↓
ASYNC PROVIDER DELIVERY

If the required outbox write fails before commit:

- authoritative mutation must not commit
- HTTP failure is legitimate

If it succeeds:

- later provider delivery must not redefine HTTP success

### If OPTIONAL:

The authoritative mutation commits independently.

Optional notification work must not redefine HTTP success.

It may be:
- best effort,
- asynchronously queued,
- logged,
- retried by existing infrastructure.

Do not introduce a new worker unless absolutely necessary.

Reuse the existing notification/outbox architecture.

==================================================
TESTING REQUIREMENTS
==================================================

This is mandatory.

For EVERY modified route, test the relevant failure boundary.

### Response enrichment

Simulate:

authoritative mutation succeeds
+
post-commit enrichment fails

Verify one of:

A. authoritative mutation is rolled back because the read was moved inside the transaction

OR

B. HTTP still returns authoritative success without requiring the enrichment

Never allow:

COMMIT
→ enrichment failure
→ HTTP 500

for an authoritative successful mutation.

### Notification intent

Test:

1. authoritative mutation succeeds + required outbox succeeds
   → HTTP success

2. authoritative mutation + required outbox fails
   → transaction rollback + legitimate failure

3. authoritative mutation succeeds + optional notification fails
   → HTTP success

4. provider delivery failure after commit
   → originating mutation remains successful

### Display media

Test:

1. PUT mutation succeeds + broadcast succeeds
   → HTTP success

2. PUT mutation succeeds + broadcast fails
   → HTTP success

3. DELETE mutation succeeds + broadcast fails
   → HTTP success

4. persisted state remains correct

5. later read/refresh still returns correct media state

### Create-route retry safety

For each modified CREATE route, explicitly inspect response-loss retry behavior.

If a duplicate can occur:

- do NOT invent a solution
- document it as a remaining Phase 3/Phase 4 reliability risk
