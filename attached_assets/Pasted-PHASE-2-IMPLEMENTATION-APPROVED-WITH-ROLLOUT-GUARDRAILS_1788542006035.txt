IMPLEMENT THE APPROVED DESIGN
==================================================

Implement the checkout-specific operation identity system described in your proposal:

1. Add checkout_operations durable storage.

2. Bind each operation to:
   - operation ID
   - actor
   - command
   - attendance
   - optional custody episode
   - original outcome
   - authoritative result
   - resolved pickup IDs
   - timestamps

3. Acquire operation-ID advisory lock BEFORE the existing child/service-date lock.

4. On first request:
   - validate
   - authorize
   - execute the existing Phase 1 authoritative checkout
   - persist the completed operation result inside the transaction
   - commit
   - return authoritative result

5. On retry with the SAME operationId:
   - verify actor/command/resource binding
   - do NOT execute checkout again
   - do NOT create duplicate notification intents
   - return the original authoritative result
   - return original resolved pickup IDs
   - return already_applied

6. Handle operation-ID collisions safely:
   - same ID + different resource/command/actor = generic conflict/not-found semantics
   - never disclose another actor's operation

7. Add the checkout-scoped reconciliation endpoint:

GET /api/attendance/{attendanceId}/checkout-operations/{operationId}

The endpoint MUST acquire the operation-ID lock before checking the operation record so that an in-flight transaction cannot incorrectly appear as "not found."

8. Reconciliation MUST be actor-bound and must not become an operation enumeration mechanism.

==================================================
UNKNOWN NETWORK RESULT
==================================================

This is the most important behavioral requirement.

If the checkout request fails because the client cannot determine whether the server committed:

DO NOT display:

"Checkout failed"

Classify the result as UNKNOWN.

Attempt authoritative reconciliation using the same operationId.

If reconciliation confirms success:
- show checkout success
- remove pending operation
- refresh attendance separately

If reconciliation confirms operation was not committed:
- show an appropriate unconfirmed/retry state
- retain/reuse the operation identity

If reconciliation itself fails:
- show "Checkout status is temporarily unknown"
- preserve the operation identity
- allow "Check status" and "Retry"

A network error is NOT equivalent to a business rejection.

HTTP 4xx domain rejection may remain a definitive rejection, subject to the classification defined in the approved design.
