==================================================
APPROVED CHILD CHECKOUT FIX
==================================================

PUT /attendance/:id/checkout

must become an idempotent one-way transition.

Required:

1. Only a record not already picked_up may perform the authoritative checkout transition.
2. Only the winning transition writes:
   - check_out_time
   - checked_out_by
   - status
3. Only the winning transition triggers checkout side effects.
4. An exact retry returns HTTP 200 with the existing completed attendance record.
5. A retry must NOT:
   - change checkout timestamp
   - change checkout actor
   - send notifications again
6. Four simultaneous requests must result in exactly one authoritative transition.

Prefer a conditional PostgreSQL UPDATE with the expected state in the WHERE
predicate.

Do not depend on frontend state for idempotency.

==================================================
ARRIVAL FIX
==================================================

PUT /attendance/:id/arrive

must use the same conditional-transition principle.

Only one request may perform the transition to in_class.

Concurrent/repeated arrival must not:

- rewrite arrival timestamp
- rewrite confirming teacher
- repeat arrival notifications

Preserve existing successful retry semantics where compatible.

==================================================
CHILD CHECK-IN
==================================================

Preserve the existing:

- child/date advisory lock
- child/date/slot unique constraint
- opposing-service validation
- intentional bothServices behavior

Do not replace these mechanisms.

RETRY OF SAME OFFLINE EVENT

from

LEGITIMATE NEW CHECK-IN AFTER PICKUP

A repeated accepted logical event must not repeat notifications.

A genuinely new event after pickup must remain capable of creating the
existing intended fresh check-in behavior.

Keep it minimal and attendance-specific.

Expected information:

- event ID
- originating/authenticated user ID
- operation
- resulting attendance record reference where applicable
- creation/processing timestamp

Approved uniqueness concept:

(user_id, event_id, operation)

Do not turn this into a general application idempotency platform.

The processed-event record and attendance mutation must be transactionally
consistent.

A duplicate event must return the already accepted logical result without
repeating side effects.

LOGOUT / ACCOUNT SWITCH
==================================================

On logout:

clear the active user's pending attendance queue according to the approved
Phase 4 policy.

Do not leave a globally reusable queue.

User B login must never inherit User A's attendance events.

Do not migrate events between users.

==================================================
ROLE REMOVAL / SUSPENSION
==================================================

Every offline sync must run current server-side authentication and
authorization checks.

If since queue creation the user:

- lost the selected role
- was suspended
- became inactive
- no longer has access to the target object

the queued operation must not execute.

Phase 1 authentication remains authoritative.
