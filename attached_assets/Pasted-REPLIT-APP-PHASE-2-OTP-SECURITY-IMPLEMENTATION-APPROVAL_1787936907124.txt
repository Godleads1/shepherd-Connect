==================================================
PROVIDER FAILURE
==================================================

Persist the OTP session before attempting delivery.

Do not hold database locks during provider network calls.

Provider helper behavior must stop swallowing definitive final failure.

A successful response must not claim delivery unless delivery is actually
known.

Distinguish provider acceptance/queueing from actual delivery.

On definite delivery-provider failure or bounded timeout:

- invalidate/expire the new OTP session
- retain sufficient issuance history for the rolling abuse limit
- return generic 503
- do not expose provider internals
- do not expose OTP

Provider failures may count toward the abuse window so provider outages
cannot be hammered indefinitely.

FAILED ATTEMPT POLICY
==================================================

- durable in PostgreSQL
- atomic increment
- fifth failed attempt makes OTP unusable
- correct code after exhaustion fails
- IP rate limiting is NOT a substitute for credential attempt counting

==================================================
ATOMIC VERIFICATION
==================================================

One registration OTP may successfully transition to VERIFIED at most once.

Use a PostgreSQL conditional atomic mutation.

Required predicates include:

- correct pinId
- correct HMAC
- not expired using database time
- attemptCount below limit
- verifiedAt IS NULL

Successful transition:

verifiedAt = database now()

Only one concurrent correct verification request may succeed.

Do not implement read → compare → delete as separate unprotected steps.

==================================================
ATOMIC REGISTRATION CONSUMPTION
==================================================

Inside the same PostgreSQL transaction as the registration mutation:

1. validate registration request
2. normalize the relevant contact
3. atomically consume the verified otpPinId
4. require:
   - verifiedAt IS NOT NULL
   - still within permitted validity
   - contact matches the contact being registered
5. perform the applicable registration mutation:
   - new user
   - approved secondary role
   - pending role
6. commit

One verified OTP proof may authorize at most ONE registration mutation.

If the registration mutation fails:

transaction rollback must preserve the OTP proof where appropriate.

Two concurrent registrations using one proof must result in at most one
successful mutation.
