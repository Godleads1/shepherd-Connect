MILESTONE 10A-4 — CURRENT-PASSWORD UNICODE ALIGNMENT

Fix the remaining password-input lockout risk.

Do not stage, commit, push, migrate or deploy.

PROBLEM

The server accepts passwords up to 128 Unicode code points.

A valid stored password may require up to 256 UTF-16 units in the browser. Any sign-in or current-password input with maxlength="128" can therefore prevent the exact valid password from being entered.

CORRECTION

Change the native HTML maxlength from 128 to 256 on every remaining password input, including:

- ordinary staff sign-in password;
- invitation administrator current password;
- password-reset issuance administrator current password;
- deactivate/reactivate/reissue confirmation current password;
- own-password-change current password;
- any other field used to enter an existing staff password.

After this correction, every staff password input should have a 256 UTF-16-unit browser safety ceiling.

Do not change:

- the backend maximum of 128 Unicode code points;
- the new-password checklist;
- the Argon2 configuration;
- password normalization behavior;
- password storage;
- API schema maximums.

RATIONALE

- Browser maxlength counts UTF-16 units.
- Python/Pydantic policy counts Unicode code points.
- 128 Unicode code points require at most 256 UTF-16 units.
- The HTML value is an input safety ceiling, not the password-policy maximum.
- The backend remains authoritative at 128 code points.

CURRENT-PASSWORD BEHAVIOR

- Do not trim or normalize current passwords.
- Do not apply the new-password composition checklist to sign-in or current-password fields.
- Do not reject legacy passwords for lacking uppercase, lowercase, number or symbol.
- Continue allowing existing legacy hashes to verify and rehash transparently.
- Never send a password while the user is merely typing.
- Existing-password fields may allow more than 128 BMP characters to be typed, but the API safely rejects values beyond its 128-code-point bound.

TESTS

Add tests proving:

1. Every password input has maxlength="256".
2. Sign-in can accept a stored password containing exactly 128 Unicode code points and 256 UTF-16 units.
3. Own-password-change current-password input can accept the same password.
4. ADMIN step-up fields can accept the same password.
5. The value is sent exactly as typed.
6. No trimming or normalization occurs.
7. Sign-in/current-password fields do not display or apply the new-password checklist.
8. Backend request schemas still reject more than 128 Unicode code points.
9. Existing legacy-password login and transparent rehash tests remain passing.
10. New-password checklist behavior remains unchanged.
