==================================================
PHASE 3 OBJECTIVE
==================================================

Identify mutation endpoints where:

1. an authoritative business state transition is successfully committed, BUT
2. additional secondary work occurs before the HTTP response is returned, AND
3. failure of that secondary work can cause the client to receive a failure even though the authoritative mutation already committed.

The central question is:

"Can anything after the authoritative business transition make a successfully committed mutation look like a failed mutation?"

We are NOT assuming the answer is yes for every route.

Find and prove the actual cases.

==================================================
ARCHITECTURAL PRINCIPLE
==================================================

Use this model:

CLIENT COMMAND
    ↓
AUTHORIZATION / CAPABILITY CHECK
    ↓
VALIDATION
    ↓
DB TRANSACTION
    ↓
AUTHORITATIVE BUSINESS TRANSITION
    ↓
PERSIST REQUIRED OUTBOX / OPERATION RESULT
    ↓
COMMIT
    ↓
HTTP SUCCESS RESPONSE

Secondary effects such as:

- notification delivery
- realtime broadcast
- SSE
- WebSocket
- cache invalidation
- polling refresh
- analytics
- external provider calls
- media/TV synchronization
- non-authoritative reads
- formatting/enrichment queries
- cleanup
- audit side effects
- external API calls

must NOT be able to redefine the authoritative mutation outcome after commit.

Some secondary work may legitimately happen before commit if it is genuinely part of the atomic business transaction. Do not classify something as a defect merely because it happens before response.

==================================================
STEP 2 — CLASSIFY EVERY SECONDARY ACTION
==================================================

For each mutation, classify post-transition work as one of:

A. AUTHORITATIVE
    Required for the business transition itself and correctly atomic.

B. TRANSACTIONAL OUTBOX / DURABLE INTENT
    Correctly persisted as part of the transaction and safe to process later.

C. REQUIRED PRE-COMMIT VALIDATION
    Must happen before commit because it determines whether the mutation is valid.

D. NON-AUTHORITATIVE POST-COMMIT WORK
    Should not redefine mutation success.

E. UNKNOWN / NEEDS INVESTIGATION

Pay particular attention to code shaped like:

try {
    await db.transaction(...)
    await somethingElse()
    return res.json(...)
} catch {
    return failure(...)
}

or:

await db.transaction(...)
await broadcast(...)
await fetch(...)
await refresh(...)
res.json(...)

or:

const result = await mutate()
const extra = await readSomething()
return combinedResponse

The exact code does not need to match these examples.

==================================================
STEP 3 — TRACE THE COMMIT BOUNDARY
==================================================

For every potentially risky mutation, explicitly answer:

1. What exact database change represents the authoritative business outcome?

2. When does that change become durable?

3. Is the transaction definitely committed before secondary work executes?

4. What happens if secondary work throws?

5. What HTTP status/code does the client receive?

6. What message does the frontend display?

7. Does the frontend interpret that as:
   - definitive rejection
   - successful mutation
   - unknown outcome
   - refresh failure
   - something else?

8. Can the user safely retry?

9. If they retry, can it duplicate or corrupt the authoritative state?

==================================================

Search for these patterns:

1. Mutation + DELETE cleanup
2. Mutation + refetch inside same try/catch
3. Mutation + realtime broadcast
4. Mutation + notification delivery
5. Mutation + external provider call
6. Mutation + media/TV update
7. Mutation + secondary DB read
8. Mutation + response enrichment
9. Mutation + cache invalidation
10. Mutation + background-job invocation
11. Mutation + audit operation
12. Mutation + formatting/serialization query
13. Mutation + multiple independent API calls
14. Mutation + frontend cleanup
15. Mutation + optimistic UI rollback
16. Mutation + polling/SSE synchronization

Also search for broad catch blocks where one error message covers multiple operations.

==================================================
STEP 6 — FRONTEND ERROR SEMANTICS
==================================================

For every server-side false-failure candidate, trace the corresponding frontend.

Determine:

- mutation helper

==================================================
STEP 7 — CHECK FOR COMMIT + RESPONSE-CONSTRUCTION RISKS
==================================================

Search for routes where the transaction commits and then the application performs additional reads before constructing the response.

Example:

await tx.commit()

const enriched = await getSomethingElse()

res.json({
   authoritativeState,
   enriched
})

If `getSomethingElse()` fails, determine whether the endpoint incorrectly returns an error despite the authoritative mutation already being committed.

Flag these separately from notification/realtime problems.

==================================================
STEP 8 — CHECK BACKGROUND WORK
==================================================

Determine whether background work is:

- durable
- idempotent
- retryable
- transactionally enqueued
- awaited by the request
- capable of changing HTTP success/failure

Do not redesign workers.

Document only the current behavior and risk.

==================================================
STEP 9 — CHECK MULTI-STEP FRONTEND MUTATIONS
==================================================

Find frontend workflows that do something like:

1. mutation A
2. mutation B
3. refresh
4. notification
5. cleanup

inside one try/catch.

For each:

- identify which step is authoritative
- identify which steps are secondary
- identify whether failure in B/refresh/cleanup causes A to appear failed
- determine whether A can already have committed

Do not change them yet.

==================================================
STEP 10 — PRIORITIZE FINDINGS
==================================================

Assign severity:

CRITICAL
- committed authoritative state can reliably be reported as failed
- retry can create duplicate/conflicting state
- user action can become unsafe

HIGH
- committed mutation can be reported as failed
- retry may be unsafe or ambiguous
- important operational workflow affected

MEDIUM
- misleading failure is possible but retry is generally safe
- secondary effect failure affects UX/consistency

LOW
- cosmetic/non-authoritative inconsistency
- no durable business-state risk

INFO
- architecture is already correct
- no action required
