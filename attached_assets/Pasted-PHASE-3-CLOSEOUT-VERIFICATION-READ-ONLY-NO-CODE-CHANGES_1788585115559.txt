PART B — CREATE RESPONSE-LOSS DUPLICATION AUDIT
==================================================

We are NOT implementing idempotency.

We only want an evidence-based inventory.

Identify CREATE or command-style endpoints where:

1. authoritative state can commit,
2. HTTP response can be lost after commit,
3. client may reasonably retry,
4. retry could create duplicate/conflicting durable state.

For each candidate determine whether existing protection already exists.

Check:

- database unique constraints
- natural business keys
- event IDs
- stable caller IDs
- domain idempotency
- existing request identities
- duplicate detection
- frontend behavior
- generated client behavior
- server retry behavior
- transaction semantics

Do not treat "the frontend probably won't retry" as protection.

PART C — CLASSIFY RESPONSE-LOSS RISK
==================================================

For every create/command candidate assign:

SAFE
- retry cannot duplicate/conflict due to existing authoritative protection.

LOW
- duplicate is technically possible but operational impact is minimal.

MEDIUM
- duplicate is possible and materially affects data/UX.

HIGH
- duplicate/conflicting state is likely and operationally significant.

CRITICAL
- duplicate retry can cause serious business/security/safety consequences.

Include exact route and protection.
