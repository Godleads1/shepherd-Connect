==================================================
LOCKING RULE
==================================================

For every role mutation affecting an existing user:

1. start or reuse a PostgreSQL transaction
2. lock the target user row using SELECT ... FOR UPDATE
3. only AFTER the lock:
   - read primary role
   - read secondary roles
   - read pending roles
   - run duplicate checks
   - run current-role policy checks
   - calculate new role state
4. write the final canonical result
5. commit
6. perform notifications after commit

Do not:

READ role state
→ later lock
→ write stale state

The lock must protect the decision itself, not just the final UPDATE.

==================================================
ROLE SET INVARIANTS
==================================================

Within the locked transaction, preserve canonical set-like role behavior.

Required:

- known role names only
- no duplicate secondary role
- no duplicate pending role
- primary role must not also appear in secondary roles
- approving one pending role removes only that pending role
- rejecting one pending role removes only that pending role
- granting one secondary role preserves all unrelated approved roles
- revoking one secondary role preserves all unrelated approved roles
- a removed role must not be resurrected by a concurrent stale writer

Do not silently change role priority or approval policy.

==================================================
REGISTRATION + OTP
==================================================

Preserve Phase 2 one-proof-one-mutation semantics.

For an existing user registration request:

verified OTP proof
→ consume proof inside transaction
→ lock existing user
→ read authoritative current role state
→ validate current policy
→ mutate pending/secondary role
→ commit

If the role mutation fails:

the OTP proof consumption must roll back.

If two distinct valid proofs simultaneously request different roles for
the same user:

both valid requests must serialize on the user row.

Expected durable result:

both legitimate role outcomes survive.

==================================================
ROLE APPROVAL / REJECTION
==================================================

POST /api/users/:id/approve-role

must:

- lock user
- read current pending + secondary roles after lock
- confirm requested role state using existing policy
- add approved role once
- remove only that role from pending
- preserve unrelated pending roles
- preserve unrelated approved roles

POST /api/users/:id/reject-role

must:

- lock user
- remove only the intended pending role
- preserve all others

Notifications must occur only after successful commit.

==================================================
GRANT / REVOKE
==================================================

POST /api/users/:id/grant-role

must preserve unrelated secondary roles and avoid duplicates.

DELETE /api/users/:id/grant-role/:role

must remove only the specified role and must not resurrect or erase
unrelated roles.

Both must serialize on the user row.
