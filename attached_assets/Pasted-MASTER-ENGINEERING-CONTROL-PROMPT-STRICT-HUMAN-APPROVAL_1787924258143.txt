============================================================
DESTRUCTIVE ACTION RULE
============================================================

Actions involving:

- deleting users
- deleting records
- changing user roles
- changing permissions
- changing passwords
- disabling users
- removing teachers/admins
- changing ownership
- bulk edits
- database migrations
- irreversible actions

require additional caution.

Never execute or implement a destructive action merely because the user
clicked a button.

Verify:

1. user identity
2. authorization
3. target record
4. requested action
5. confirmation
6. server-side permission
7. database result

The backend must be authoritative.

Frontend visibility of a button is NOT authorization.

============================================================
CRITICAL CONSISTENCY RULE
============================================================

The application must never produce contradictory behavior such as:

ACTION ATTEMPT 1:
"Invalid"
but operation actually succeeds later.

ACTION ATTEMPT 1:
"Cannot delete user"
ACTION ATTEMPT 2:
user is deleted.

ROLE SWITCH:
error shown
but role/state changes anyway.

If an operation succeeds in the database, the frontend must eventually
display success.

If an operation fails in the database, the frontend must not pretend it
succeeded.

There must be one authoritative result.

Investigate mismatches between:

frontend status
API status
database status

before changing anything.

============================================================

The current application has observed intermittent clock-in behavior.

Example:

First clock-in attempt:
"Invalid"

Later:
operation works or appears successful.

Treat this as a HIGH-PRIORITY CONSISTENCY BUG.

Trace:

clock-in button
→ frontend validation
→ timestamp/timezone logic
→ API request
→ authentication/session
→ attendance validation
→ duplicate detection
→ database transaction
→ response status
→ frontend state
→ displayed message

Check specifically for:

- duplicated clock-in requests
- stale attendance state
- race conditions
- asynchronous request ordering
- premature validation messages
- database commit occurring after UI error
- retry behavior

Do NOT patch any of these until the actual cause is confirmed.

============================================================
USER DELETE CONTROL
============================================================

Observed behavior:

Attempt 1:
application says user cannot be deleted.

Attempt 2:
same user can be deleted.

Treat this as a HIGH-PRIORITY AUTHORIZATION/STATE CONSISTENCY BUG.

Trace:

delete button
→ confirmation
→ target user ID
→ requesting user identity
→ role/permission evaluation
→ API request
→ backend authorization
→ dependency/relationship checks
→ database transaction
→ deletion result
→ API response
→ frontend refresh

Check for:

- stale user list
- incorrect target ID
- race condition
- soft-delete/hard-delete mismatch
- foreign-key dependency timing
- frontend error while backend succeeds
- duplicate requests
- authorization state changing between requests
- cached permission state
- database transaction not committed when response is generated

Deletion permission MUST be enforced server-side.

Never rely solely on frontend controls.

============================================================
TEACHER ROLE SWITCHING CONTROL
============================================================

Observed behavior:

Switching into or out of the Teacher role sometimes produces an error.

Treat this as a HIGH-PRIORITY ROLE/AUTHORIZATION CONSISTENCY BUG.

Trace:

role selector
→ frontend role state
→ API request
→ authenticated user
→ authorization policy
→ database role update
→ token/session claims
→ session refresh
→ frontend state refresh
→ route permissions
→ resulting UI

Check specifically for stale JWT/session claims.

If the database role changes but the existing session/token still contains
the old role, the application can temporarily disagree about the user's
permissions.

Do NOT automatically refresh or rewrite authentication until this is
confirmed.

============================================================
DATABASE TRANSACTION RULE
============================================================

For write operations:

success must only be reported after the authoritative database operation
has succeeded.

If a transaction fails:

ROLLBACK.

Do not report success.

If a transaction succeeds:

COMMIT.

Then return the authoritative result.

Avoid situations where:

UI reports failure
but DB commits

or:

UI reports success
but DB rolls back.

============================================================
DUPLICATE REQUEST / IDEMPOTENCY RULE
============================================================

For actions that may be submitted twice because of:

double click
network retry
slow response
mobile reconnect
UI retry

investigate duplicate request handling.

Where appropriate:

- disable button while request is in flight
- use server-side idempotency
- reject duplicate active operations safely
- return the original successful result for safe retries

Do not implement idempotency without approval.

============================================================
LOADING STATE RULE
============================================================

An action button should not remain freely clickable while its request is
still executing if duplicate requests could cause inconsistent state.

Investigate whether affected controls properly represent:

idle
loading
success
failure

Do not display "invalid" while the server request is still unresolved.
